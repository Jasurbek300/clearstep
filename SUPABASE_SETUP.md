# Supabase для ClearStep

Подключённый проект Supabase уже прописан в `js/config.js`; по сообщению владельца аккаунты и облачное сохранение работают. Если вход и синхронизация уже проходят, создавать новый проект или менять ключи не нужно. Эта инструкция нужна для проверки провайдеров, адресов возврата и восстановления настройки при переносе проекта.

## 1. Если подключение перестало работать
Откройте тот Supabase-проект, который уже используется ClearStep. Не создавайте второй проект без необходимости: данные аккаунтов и прогресс останутся в исходном проекте.

## 2. Создайте таблицу и правила доступа
1. Откройте **SQL Editor → New query**.
2. Вставьте содержимое файла `supabase/schema.sql` и нажмите **Run**. Если таблица уже создавалась, запустите обновлённый файл повторно: он добавляет атомарное сохранение прогресса для нескольких устройств.
3. Проверьте: **Table Editor → user_progress** существует, у неё включён **RLS** (Row Level Security).

## 3. Проверьте публичную конфигурацию
В **Project Settings → API** проверьте, что URL и публичный ключ совпадают с `js/config.js`. При намеренной смене проекта обновите эти значения:
   ```js
   window.CS_CONFIG = { SUPABASE_URL: "https://xxxx.supabase.co", SUPABASE_ANON_KEY: "..." };
   ```
3. **Никогда** не вставляйте ключ `service_role` в сайт или репозиторий. Ключ `anon` публичный по замыслу: данные защищает RLS.

## 4. Адреса сайта
**Authentication → URL Configuration**
- **Site URL:** `https://maksimalek121213-spec.github.io/ClearStep/`
- **Redirect URLs:** добавьте тот же адрес (с `/ClearStep/` на конце). Без этого ссылки из писем и Google вернут на неправильную страницу.

## 5. Вход по почте и паролю + ссылка на почту
**Authentication → Providers → Email**: включено.
- **Confirm email**: включите, чтобы регистрация требовала подтверждения почты.
- Magic link работает через тот же провайдер.
- Встроенная отправка писем Supabase имеет жёсткий лимит (несколько писем в час). Для реального запуска подключите свой SMTP: **Project Settings → Authentication → SMTP Settings**.

## 6. Google
1. https://console.cloud.google.com → создайте проект → **APIs & Services → OAuth consent screen** (External).
2. **Credentials → Create credentials → OAuth client ID → Web application.**
3. В **Authorized redirect URIs** вставьте адрес из Supabase: **Authentication → Providers → Google** (вида `https://xxxx.supabase.co/auth/v1/callback`).
4. Скопируйте **Client ID** и **Client secret** в Supabase (**Providers → Google → Enable**). Секрет вводится только в панели Supabase, не в код.

## 7. Приёмочная проверка владельцем проекта
Эти сценарии требуют входа в реальный аккаунт и должны быть проверены после настройки провайдеров:
- [ ] Регистрация, письмо подтверждения, вход
- [ ] Выход и повторный вход
- [ ] Забыли пароль: письмо, форма нового пароля
- [ ] Ссылка для входа по почте
- [ ] Вход через Google
- [ ] Пройти вопросы на одном устройстве, войти с другого: прогресс на месте
- [ ] Одновременно сохранить разные попытки с двух устройств: обе видны после перезагрузки
- [ ] Выключить интернет: статус «Нет сети», затем «Сохранено» после возвращения
- [ ] Удаление аккаунта: пользователь и строка в `user_progress` исчезли
- [ ] Второй аккаунт не видит чужой прогресс

## Обновление атомарной синхронизации

Последняя схема добавляет RPC `save_my_progress`. Она объединяет историю ответов и попыток тестов в одной транзакции базы данных, чтобы почти одновременные сохранения с разных устройств не затирали разные попытки друг друга. Для одного и того же поля, изменённого одновременно на двух устройствах (например, заметки к одному вопросу), действует правило: побеждает снимок с более поздним временем изменения. После запуска схемы вернитесь на сайт и перезагрузите страницу.
